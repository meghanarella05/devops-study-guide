Data Organization, Processes & Memory

Databases · Schemas · Tablespaces · Files · TOAST · Processes
🗄️ Cluster, Databases & System Catalog ▼

A PostgreSQL instance (server) manages a database cluster — a collection of databases sharing the same data directory (PGDATA).

After initialization, PGDATA contains three databases:

  • template0 — never modified; used for restores or new DBs with different encoding
  • template1 — template for CREATE DATABASE
  • postgres — default user database

The system catalog stores metadata (tables, indexes, types, functions) in tables named pg_*. Each database has its own catalog; some tables are cluster-wide. The primary key column is always called oid (a 32-bit integer object identifier).

Column names use 3-letter prefixes matching the table name (e.g., datname in pg_database).
📁 Schemas & Tablespaces ▼

Schemas are logical namespaces within a database. Predefined schemas:

  • public — default for user objects
  • pg_catalog — system catalog tables
  • information_schema — SQL-standard view of catalog
  • pg_toast — TOAST objects
  • pg_temp — alias for current session's temp tables (pg_temp_N)

Tablespaces define physical layout (a directory on disk). Logical and physical structures are independent. Default tablespaces:

  • pg_default → PGDATA/base
  • pg_global → PGDATA/global (cluster-wide catalog)
Custom tablespaces are symlinked from PGDATA/pg_tblspc. All paths are relative to PGDATA.
📂 Files, Forks & Pages ▼

Each relation (tables, indexes, sequences, materialized views) is stored in forks:

  • Main fork — actual row/index data (named by relfilenode)
  • Free space map (FSM) — tracks available space within pages (_fsm suffix)
  • Visibility map (VM) — two bits per page: all-visible & all-frozen (_vm suffix)
  • Initialization fork — for unlogged tables only (_init); replaces main fork on crash recovery
Files grow in 1 GB segments. Small table with TOAST = at least 8 files (3 main + 3 TOAST table + 2 TOAST index).

Pages (blocks) are the unit of I/O — default 8 kB, configurable only at build time (--with-blocksize, up to 32 kB).

🍞 TOAST (Oversized Attribute Storage) ▼

Rows must fit a single page. For large values, TOAST applies:

  • plain — no TOAST (small fixed types like integer)
  • extended — compress first, then move to TOAST table if still too big (default for text/json)
  • external — move to TOAST table uncompressed
  • main — compress first, only move as last resort (numeric)

TOAST algorithm triggers when row exceeds ~2000 bytes (¼ of page). Threshold can be changed with toast_tuple_target.

For indexes, TOAST supports compression only — no separate table. Avoid bulk binary data in PG if not needing transactional logic.

Access to columns NOT in the query means TOAST table is never read — avoid SELECT *.

⚙️ Processes & Memory ▼

postmaster — the first process; spawns all others, handles incoming connections by forking a new backend process per client.

Key background processes:

  • startup — crash recovery
  • autovacuum launcher/worker — dead tuple cleanup
  • wal writer — flushes WAL to disk
  • checkpointer — periodic checkpoints
  • writer (bgwriter) — flushes dirty pages
  • stats collector — usage statistics
  • wal sender/receiver — replication

All processes share shared memory. The buffer cache takes the largest portion — caches recently read pages.

Connection pooling (PgBouncer, Odyssey) is needed because each client = 1 backend process with its own memory.

Isolation

ACID · Anomalies · Isolation Levels · MVCC
⚠️ Concurrency Anomalies ▼
  • Lost Update — T1 and T2 read same row; T1 updates; T2 updates based on stale read → T1's change is lost
  • Dirty Read — reading uncommitted changes of another transaction
  • Non-Repeatable Read — same row read twice; another transaction updates/deletes it between reads → different results
  • Phantom Read — same query run twice; another transaction inserts/deletes rows matching the condition → different row sets
  • Read Skew — reading different rows from different snapshots within one transaction (PG-specific)
  • Write Skew — two transactions read overlapping data, each decides it's safe to update different parts → consistency broken
  • Read-Only Transaction Anomaly — read-only transaction sees inconsistent state due to ordering of concurrent writers
📊 SQL Standard vs PostgreSQL Isolation Levels ▼

SQL Standard allows:

PostgreSQL (MVCC-based, stricter):

Read Uncommitted in PG behaves identically to Read Committed — dirty reads are impossible by design with MVCC.
🔵 Read Committed — Details ▼

Default level (default_transaction_isolation). Snapshot taken per statement.

  • No dirty reads ✓
  • Non-repeatable reads allowed
  • Classic anti-pattern: IF SELECT >= X THEN UPDATE — the check is useless because state can change between operators

Read Skew at RC: reading Bob's two accounts in two statements while a transfer commits in between → wrong total.

Fix patterns:

  • Single SQL operator (SELECT sum(amount) FROM accounts WHERE client='bob')
  • Declarative CHECK constraint instead of procedural logic
  • Explicit locking (SELECT FOR UPDATE, LOCK TABLE) — last resort
VOLATILE functions in RC can see different data from the main query — a subtle trap since both are PG defaults.
🟡 Repeatable Read — Details ▼

Snapshot taken at first statement of transaction; held for the whole transaction. Eliminates non-repeatable reads AND phantom reads.

Serialization failures replace anomalies: if a concurrent update would create a read skew, the transaction aborts with ERROR: could not serialize access due to concurrent update.

⚠️ Applications MUST retry transactions on serialization failures at Repeatable Read (and Serializable) levels.

Still allows: Write Skew and Read-Only Transaction Anomaly.

Use case: Read-only multi-query reports — perfect complement to RC.

🔴 Serializable — Details ▼

Prevents ALL anomalies. Built on top of Snapshot Isolation + SSI (Serializable Snapshot Isolation).

  • Write skew and read-only anomalies are detected and cause serialization failures
  • False positives possible — safe transactions may be aborted due to lack of index info or RAM
  • All transactions in the app must use Serializable for it to work properly
  • Not supported on replicas
  • Cannot be mixed with other levels (behaves as RR if mixed)

DEFERRABLE option: BEGIN ISOLATION LEVEL SERIALIZABLE READ ONLY DEFERRABLE — blocks until safe to execute without any anomaly risk. Only case where SELECT can block.

Modify default_transaction_isolation to ensure all transactions use Serializable if you adopt this level.
🎯 Which Level to Use? ▼
  • Read Committed — default, no retries needed, but developer must prevent anomalies via careful SQL design
  • Repeatable Read — great for read-only transactions (reports); requires retry logic for write transactions
  • Serializable — simplest logic for developers; requires retry logic, not on replicas, may reduce throughput

Pages & Tuples

Page Layout · Row Version Headers · MVCC Mechanics · Subtransactions
📄 Page Structure ▼

Each 8 kB page contains (low → high address):

  1. Page header — checksum, sizes, free space boundaries (lower/upper)
  2. Item pointer array — 4-byte pointers (offset + length + status bits); grows downward
  3. Free space — between pointers and tuples
  4. Tuples — actual row data; grow upward from high address
  5. Special space — for indexes (B-tree metadata, etc.); zero size in table pages
No fragmentation — free space is always one contiguous chunk. Tuples can be moved within the page; the pointer is updated, but the TID (page#, pointer#) stays the same.
🔖 Row Version (Tuple) Header ▼

Each tuple has a header (minimum 23 bytes, often more due to NULL bitmap and alignment):

  • xmin — XID of the INSERT transaction that created this version
  • xmax — XID of the DELETE/UPDATE transaction that obsoleted this version (0 = alive)
  • infomask — hint bits including xmin_committed, xmin_aborted, xmax_committed, xmax_aborted
  • ctid — pointer to the next version of this row (for updates)
  • cmin/cmax — command sequence within current transaction (for cursor visibility)
  • null bitmap — marks NULL columns
Indexes do NOT have xmin/xmax — they point to ALL versions; visibility is checked by accessing the heap (or visibility map for index-only scans).
✏️ Tuple Operations (INSERT/UPDATE/DELETE) ▼

INSERT: New tuple written with xmin = current_txid, xmax = 0 (with xmax_aborted bit set). xmin_committed bit set later by first reader after commit.

DELETE: xmax set to deleting XID. No data physically removed. xmax_aborted bit cleared. When DELETE commits → xmax_committed set by next reader.

UPDATE: = DELETE old version + INSERT new version. Old tuple gets xmax = updating XID. New tuple has same xmin = that XID. Old tuple's ctid → new tuple.

ROLLBACK: Does NOT reverse changes in data pages — just marks transaction as aborted in CLOG. Next reader sees aborted status and ignores the tuple.

Hint bits cache the commit/abort status in the tuple header to avoid re-reading CLOG on every access. SET by any transaction, even read-only ones (making them "dirty" pages).
CLOG (commit log) lives in PGDATA/pg_xact. It stores 2 bits per XID: committed + aborted.
🌀 Virtual Transactions & Subtransactions ▼

Virtual XIDs: read-only transactions get a virtual ID (backend PID + sequence) to avoid consuming real XIDs. Real XID assigned only on first write.

Subtransactions (Savepoints):

  • Each savepoint creates a subtransaction with its own XID (larger than parent's)
  • Status stored in PGDATA/pg_subtrans
  • If parent aborts → all subtransactions considered aborted
  • Committed subtransactions get BOTH committed AND aborted bits set in CLOG — final decision depends on parent
psql's \set ON_ERROR_ROLLBACK on adds implicit savepoints before each command — useful but adds overhead even when not needed.

Snapshots

Snapshot Structure · Visibility Rules · Transaction Horizon
📸 What is a Snapshot? ▼

A snapshot defines which row versions are visible to a transaction. It is NOT a physical copy — it's a set of numbers that determine visibility rules.

When taken:

  • Read Committed: at the start of each statement
  • Repeatable Read / Serializable: at the start of the first statement of the transaction
🔢 Snapshot Structure: xmin, xmax, xip_list ▼

A snapshot consists of three values (visible as pg_current_snapshot() → xmin:xmax:xip_list):

  • xmin — XID of oldest active transaction at snapshot creation. All XIDs < xmin are committed (visible) or aborted (ignored).
  • xmax — one past the XID of the latest committed transaction. All XIDs ≥ xmax are not visible (future or running).
  • xip_list — list of XIDs of transactions that were active at snapshot creation (except virtual ones)

Visibility rule: A tuple is visible if:

  • xmin < snapshot.xmin → always visible (if committed)
  • snapshot.xmin ≤ xmin < snapshot.xmax → visible only if NOT in xip_list (and committed)
  • xmin ≥ snapshot.xmax → not visible
PG cannot do "flashback" queries — commit times are not tracked in a way that allows recreating past snapshots.
🌅 Transaction Horizon & Vacuuming ▼

The horizon of a transaction = its snapshot's xmin. Tuples with xmax < horizon are invisible to all current/future transactions and can be vacuumed.

The database horizon = oldest xmin of all active transactions. Vacuum can only remove tuples beyond this horizon.

⚠️ A long-running transaction holds the database horizon, preventing vacuum from cleaning up dead tuples — leading to table bloat.
  • Repeatable Read / Serializable: holds horizon for entire transaction duration
  • Read Committed (real XID): holds horizon even when idle ("idle in transaction")
  • Read Committed (virtual XID): holds horizon only during statement execution

Monitor: pg_stat_activity.backend_xmin

📤 Exporting Snapshots ▼

Use pg_export_snapshot() to get a snapshot ID that another transaction can import with SET TRANSACTION SNAPSHOT '...'. Requires Repeatable Read or Serializable level.

Used by pg_dump --parallel so all workers see the same consistent state.

Page Pruning & HOT Updates

Lightweight cleanup · Heap-Only Tuples · Chain updates
✂️ Page Pruning ▼

A fast, single-page cleanup triggered during reads or writes when:

  • Previous UPDATE couldn't fit new tuple in same page
  • Page data exceeds fillfactor percent

Removes tuples beyond the database horizon. Pruned pointers become dead (not freed) because indexes may still reference them. Dead pointers are cleared during index scans (marked dead in index too).

Does NOT update visibility map or free space map (so recovered space is for updates, not inserts). Does NOT touch indexes.
🔥 HOT Updates (Heap-Only Tuple) ▼

When an UPDATE modifies no indexed columns, PG uses HOT to avoid creating new index entries:

  • Old tuple marked Heap Hot Updated (HHU bit) → ctid points to new version
  • New tuple marked Heap Only Tuple (HOT bit) → not in any index
  • Index keeps only ONE entry pointing to the chain head

Index scan follows HHU chain, checking visibility of each version. Chain stays within ONE page (no cross-page chains → no extra I/O).

HOT dramatically reduces index bloat for frequently updated non-indexed columns. Lower fillfactor reserves space for HOT chain growth.

HOT Chain Split: If the page is full and pruning can't free space (held by active snapshot), a new chain starts in another page — the index gets a second entry. HOT benefit is lost for that update.

🔗 HOT Pruning & Redirect Pointers ▼

When a HOT chain is pruned, the head pointer (referenced by index) is converted to redirect status pointing to the current chain start. Other freed pointers get unused status (available for reuse).

Index pruning also happens before B-tree page splits — removes entries already marked dead, or entries for rows beyond the horizon (bottom-up deletion, v14).

Vacuum & Autovacuum

Phases · Thresholds · Throttling · Monitoring
🧹 Vacuum: Overview & Phases ▼

Routine VACUUM cleans the whole table and removes dead tuples from both the heap AND all indexes. Runs concurrently (does not block reads/writes, but blocks ALTER TABLE etc.).

Uses visibility map to skip already-clean pages.

Phases (per table):

  1. Heap Scan — find dead tuples; store their TIDs in a memory array (size = maintenance_work_mem / 6 bytes each)
  2. Index Vacuuming — full scan of each index to remove entries pointing to dead tuples. Can be parallel (one worker per index ≥ min_parallel_index_scan_size)
  3. Heap Vacuuming — remove actual heap tuples and free pointers (now safe since index refs removed)
  4. Repeat 1–3 if TID array fills up
  5. Heap Truncation — if ≥1/16 of table is empty pages at end, truncate file (requires brief exclusive lock, max 5 seconds wait)
If TID array fills before full scan → multiple passes = multiple full index scans. Fix: increase maintenance_work_mem or vacuum more frequently.
🤖 Autovacuum: Mechanism ▼

Autovacuum launcher runs continuously, spawning workers every autovacuum_naptime (default 1 min). Max workers: autovacuum_max_workers (default 3).

Vacuum triggered when:

  • n_dead_tup > autovacuum_vacuum_threshold (50) + autovacuum_vacuum_scale_factor (0.2) × reltuples
  • v13+: n_ins_since_vacuum > autovacuum_vacuum_insert_threshold (1000) + autovacuum_vacuum_insert_scale_factor (0.2) × reltuples

Analyze triggered when:

  • n_mod_since_analyze > autovacuum_analyze_threshold (50) + autovacuum_analyze_scale_factor (0.1) × reltuples
⚠️ autovacuum_vacuum_scale_factor = 0.2 (20%) is too large for big tables. Tune per-table with storage parameters.
First time a new table is vacuumed, reltuples = -1 (unknown), so threshold formula uses 0 → threshold = just the fixed part.
🎚️ Throttling ▼

After every vacuum_cost_limit units of "cost work", vacuum sleeps for vacuum_cost_delay.

Cost per page: vacuum_cost_page_hit (1, cached), vacuum_cost_page_miss (2, disk), vacuum_cost_page_dirty (20, dirtied by vacuum).

Manual VACUUM: vacuum_cost_delay = 0 (no sleep) by default. Autovacuum: autovacuum_vacuum_cost_delay = 2ms by default (was 20ms before v14!).

All autovacuum workers share the cost limit — adding more workers doesn't increase total I/O impact. To speed up: increase both autovacuum_max_workers AND autovacuum_vacuum_cost_limit.

📡 Monitoring ▼
  • VACUUM VERBOSE — prints detailed report after completion
  • pg_stat_progress_vacuum — live progress (phase, pages scanned/vacuumed, index_vacuum_count)
  • pg_stat_all_tables — n_dead_tup, n_ins_since_vacuum, last_autovacuum
  • log_autovacuum_min_duration = 0 — log all autovacuum runs to server log
Key signal: if index_vacuum_count > 1, maintenance_work_mem is too small — vacuum had to scan indexes multiple times.

Freezing

XID Wraparound · Frozen Tuples · Freezing Parameters
❄️ XID Wraparound Problem ▼

Transaction IDs are 32-bit integers (~4 billion). PG compares ages (modular arithmetic), not absolute XIDs. Think of XIDs on a clock face — half the circle is "past", half is "future".

Without intervention, an old XID will eventually appear to be in the "future" of newer transactions — making old changes invisible. Catastrophic!

Solution: Freezing — vacuum marks old tuples as "frozen" (both committed+aborted hint bits set). Frozen tuples are visible in all snapshots; their XID can be safely reused.

64-bit XIDs exist internally but don't go into data pages (each tuple header has 2 XIDs, adding 4 bytes per XID would be too costly).
🌡️ Four Freezing Parameters ▼
ParameterDefaultEffect
vacuum_freeze_min_age50MMin XID age before freeze. Low = more freezing overhead; high = risk of skipping hot rows.
vacuum_freeze_table_age150MWhen age(relfrozenxid) exceeds this, vacuum ignores visibility map and freezes ALL pages (aggressive mode).
autovacuum_freeze_max_age200MForces autovacuum even if disabled, to prevent wraparound. Restart required to change.
vacuum_failsafe_age1.6Bv14: if this age reached, vacuum drops index cleanup and throttling to freeze ASAP.
Each table has pg_class.relfrozenxid — all XIDs older than this are guaranteed frozen. Database has pg_database.datfrozenxid. Autovacuum uses these to decide when to force freezing.
Aggressive freezing scans every page but uses freeze map (_vm second bit) to skip already-frozen pages.
🚀 Manual Freezing ▼
  • VACUUM FREEZE table — freezes all tuples regardless of age (as if freeze_min_age = 0)
  • COPY ... WITH FREEZE — freezes tuples during initial bulk load (table must be created/truncated in the same transaction). Breaks RR/Serializable isolation slightly but usually acceptable for data loading.
After VACUUM FULL or COPY FREEZE, run regular VACUUM to set visibility map bits — otherwise even frozen pages may be revisited.

Rebuilding Tables & Indexes

VACUUM FULL · CLUSTER · REINDEX · Preventive Measures
🔨 VACUUM FULL ▼

Routine VACUUM frees space within pages but rarely reduces file size (no empty tail pages). VACUUM FULL rebuilds the entire table + all indexes from scratch:

  • Packs data as densely as possible (respects fillfactor)
  • Exclusively locks the table (blocks ALL reads and writes)
  • Needs 2× disk space temporarily (old + new files)
  • Freezes all tuples for free
  • Creates new file paths (filenames change)
After VACUUM FULL, run regular VACUUM to set visibility map — VACUUM FULL doesn't update it.

Monitor with: pg_stat_progress_cluster view

🔃 Other Rebuild Commands ▼
  • CLUSTER table USING index — rebuilds like VACUUM FULL + reorders rows by index. Physical order degrades over time (no ongoing clustering). VACUUM FULL is internally a CLUSTER without reordering.
  • REINDEX — rebuilds one or more indexes. Used by VACUUM FULL / CLUSTER internally.
  • TRUNCATE — deletes all rows by creating new empty file. Much faster than DELETE (no tuple marking, no vacuum needed). Exclusively locks table.

Zero-downtime alternatives:

  • pg_repack — rebuilds with minimal lock (exclusive only at start/end; uses trigger to replay changes)
  • pgcompacttable — fake updates to gradually move rows toward file start; then truncation; no extra space needed but slower
🛡️ Preventive Measures Against Bloat ▼

Long-running transactions + updates = bloat. Solutions:

  • Route long reads to replicas (OLAP vs OLTP separation)
  • idle_in_transaction_session_timeout (v9.6) — abort idle transactions automatically
  • old_snapshot_threshold (v9.6) — permit removing old tuples after timeout; transaction gets "snapshot too old" error if still needed

Batch large updates to avoid doubling table size:

WITH batch AS (
  SELECT id FROM table WHERE NOT processed 
  LIMIT 1000 FOR UPDATE SKIP LOCKED
)
UPDATE table SET processed = true
WHERE id IN (SELECT id FROM batch);

SKIP LOCKED allows parallel workers; vacuum can reclaim space between batches.

Practice Quiz

Tap a question, then reveal the answer

🎯 Test Your Knowledge

Q1. What are the three mandatory forks of any table, and what does each do?
Main fork (actual row data), Free Space Map (_fsm: tracks available space in each page), Visibility Map (_vm: two bits per page — all-visible and all-frozen). Unlogged tables also have an initialization fork (_init).
Q2. What is the difference between Dirty Read, Non-Repeatable Read, and Phantom Read?
Dirty Read: reading another transaction's uncommitted changes. Non-Repeatable Read: same row read twice, another TX updated/deleted it between reads → different result. Phantom Read: same query run twice, another TX inserted/deleted rows matching the WHERE clause → different row count.
Q3. In PostgreSQL, what are xmin and xmax in a tuple header, and what does xmax=0 with xmax_aborted bit set mean?
xmin = XID of the transaction that inserted this row version. xmax = XID of the transaction that deleted/updated it (0 means not deleted). xmax=0 with xmax_aborted bit set is the initial state for a live tuple — it means "no deleting transaction exists" (PG treats non-existent TX as aborted for visibility purposes).
Q4. What are hint bits, why are they set lazily, and what side effect do they have?
Hint bits cache the commit/abort status of xmin/xmax transactions in the tuple header to avoid repeated CLOG lookups. They are set lazily (by the first transaction to access the tuple after commit/abort) because at commit time PG doesn't know which pages were modified. Side effect: even read-only SELECT queries can dirty pages (requiring WAL records and eventual disk write).
Q5. What is a snapshot's xmin, xmax, and xip_list, and how do they determine tuple visibility?
xmin: oldest active XID when snapshot was taken — all older XIDs are committed or aborted. xmax: upper boundary (max committed XID + 1) — all XIDs ≥ xmax are invisible. xip_list: list of active XIDs at snapshot time — even if between xmin and xmax, these are NOT visible. A tuple is visible if its xmin transaction is committed and not in xip_list (or < xmin), AND its xmax transaction is not visible.
Q6. How does HOT update work and what are its two requirements?
HOT (Heap-Only Tuple) update avoids creating new index entries when an update doesn't modify any indexed columns AND the new tuple fits in the same page. The old tuple is marked "Heap Hot Updated" (HHU) with ctid pointing to new version; the new tuple is marked "Heap Only Tuple" (HOT) — not in indexes. Index keeps one entry pointing to chain head. Requirements: (1) updated column not in any index, (2) new tuple fits in same page.
Q7. What are the four phases of VACUUM and what can go wrong if maintenance_work_mem is too small?
Phases: (1) Heap Scan — collect dead tuple TIDs into memory array, (2) Index Vacuuming — full scan of each index to remove dead entries, (3) Heap Vacuuming — remove dead tuples from heap, (4) Heap Truncation — trim empty pages at file end. If maintenance_work_mem is too small, the TID array fills before the full scan completes → phases 1-3 must repeat multiple times → multiple full index scans = massive I/O. Monitor via index_vacuum_count in pg_stat_progress_vacuum.
Q8. Why does PostgreSQL need freezing, and what is relfrozenxid?
XIDs are 32-bit and wrap around after ~4 billion. PG compares transaction ages modularly (like a clock). Without intervention, an old XID will eventually appear "newer" than recent transactions — making old tuples suddenly invisible (catastrophic data loss). Freezing marks old tuples as visible-in-all-snapshots (both committed+aborted hint bits set), allowing their XIDs to be reused. relfrozenxid (in pg_class) is the XID below which all tuples in the table are guaranteed frozen — used to determine when aggressive/forced freezing is needed.
Q9. What is the difference between page pruning and regular VACUUM?
Page pruning: lightweight, single-page only, triggered automatically during reads/writes when page exceeds fillfactor. Does NOT touch indexes (leaves dead pointers) or update visibility/free space maps. Very fast. VACUUM: processes entire table, removes dead tuples from both heap AND all indexes, updates visibility map and free space map. Allows space to be reused for inserts. Can truncate file. Much more thorough but takes longer.
Q10. What is write skew and why doesn't Repeatable Read prevent it?
Write skew: T1 and T2 each read a set of rows satisfying a condition. Each independently decides it can safely update a DIFFERENT row. Both commit. Together their updates violate the consistency rule. Example: "total balance must be ≥ 0" — T1 sees $900 total and debits account A by $600; T2 also sees $900 and debits account B by $600; both commit → total is -$300. RR doesn't prevent this because the transactions update DIFFERENT rows (no serialization conflict is detected). Serializable level detects the read/write dependency cycle and aborts one transaction.
Q11. When does autovacuum trigger and what are the autovacuum_vacuum_scale_factor thresholds?
Dead tuples trigger: n_dead_tup > autovacuum_vacuum_threshold(50) + autovacuum_vacuum_scale_factor(0.2) × reltuples. Insert-only trigger (v13+): n_ins_since_vacuum > autovacuum_vacuum_insert_threshold(1000) + autovacuum_vacuum_insert_scale_factor(0.2) × reltuples. Analyze trigger: n_mod_since_analyze > autovacuum_analyze_threshold(50) + autovacuum_analyze_scale_factor(0.1) × reltuples. The 20% scale factor is problematic for large tables — a 10M row table needs 2M dead tuples before vacuum triggers.
Q12. What is the database horizon, and what type of transaction holds it longest?
The database horizon = the oldest xmin across all active transaction snapshots. Vacuum can only remove tuples with xmax below this horizon. Longest holders: Real transactions at any isolation level, even "idle in transaction" state, hold the horizon for their entire duration. A long-running Repeatable Read/Serializable transaction is worst since its snapshot xmin is fixed for the whole transaction. Virtual transactions at RC only hold it while executing a statement.
