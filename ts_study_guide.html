⚡ 60-Second Cram (read this even if nothing else)

  • Structural typing: TS cares about shape, not name. If it has the right fields/methods, it's compatible — no implements needed.
  • any vs unknown: any disables checking entirely. unknown is safe — you must narrow/assert before using it.
  • never = subtype of everything, occurs with unreachable code / exhaustiveness checks. any = super/subtype of everything (escape hatch).
  • Type widening: let x = 'a' widens to string; const x = 'a' stays literal 'a'.
  • interface can be declaration-merged & extended; type alias cannot be reopened but supports unions/conditional types. Interfaces extend with extends; type aliases "extend" via &.
  • Function param bivariance: method params are checked bivariantly (looser); standalone function params are checked contravariantly (stricter) under strictFunctionTypes.
  • keyof gets a union of property names; typeof gets the type of a value; T[K] is a lookup/indexed-access type.
  • Mapped types: { [K in keyof T]: T[K] } — base of Partial, Readonly, Record, Pick.
  • Conditional types: T extends U ? X : Y; infer pulls a type out mid-condition (used in ReturnType<T>).
  • Type guards: narrowing via typeof, instanceof, in, discriminated unions (a shared literal "tag" field), or a custom function isFoo(x): x is Foo.
  • Assertions are NOT casts: as / ! tell the compiler "trust me," they do nothing at runtime and can produce real bugs if wrong.
  • tsconfig: strict: true turns on strictNullChecks, noImplicitAny, strictFunctionTypes, etc. Always exam-favorite.
  • Modules vs Namespaces: use ES modules (import/export) for real projects; namespaces are legacy, mainly for global-script / ambient typing.
  • .d.ts files contain only types/declarations, never runtime code — used for @types/* packages and untyped JS interop.
  • tsc = TypeScript compiler/typechecker; it both checks types and emits JS. --noEmit checks only.
1 Introduction▶

Why TypeScript: JS lets you call methods on undefined, pass wrong arg counts, typo properties — and the bug only shows up at runtime. A type system is a set of rules a checker uses to assign types to a program and flag mismatches before running it.

Key terms

  • Type checker — validates your code against rules; catches type errors at compile time.
  • Compiler — turns TS into plain JS (downlevels new syntax for older runtimes too).
  • Static vs dynamic typing — static = checked before running (TS); dynamic = checked while running (JS).
  • TS is a superset of JS — all valid JS is (almost) valid TS.
🪤 Exam trap: TypeScript code still ultimately compiles down to JavaScript — types are erased at runtime, they have zero runtime cost/representation.
2 TypeScript: A 10,000-Foot View▶

Compiler pipeline

Code → Parser (tokens → AST) → Type checker (checks AST, infers/validates types) → Emitter (AST + types → JS). tsc can run just the checker (--noEmit) or also emit.

Core ideas

  • Type inference — TS guesses types from how you initialize/use a value, so you often don't annotate everything.
  • Structural typing — compatibility is based on members present, not declared names/inheritance (unlike Java/C#'s nominal typing).
  • TS adds types on top of JS — values still exist only at runtime; types only exist at compile time (erased after).
function add(a: number, b: number) {
  return a + b   // return type inferred: number
}
3 All About Types▶

The type universe (top → bottom)

any (top, opt-out of checking) → object types/unions → primitives → never (bottom, no values, unreachable).

Primitives & special types

  • boolean, number, string, bigint, symbol
  • Literal types: let dir: 'up'|'down' — a specific value as its own type.
  • null / undefined — with strictNullChecks, NOT assignable to other types unless explicitly unioned.
  • void — return type meaning "nothing useful returned" (functions with side effects).
  • never — function never returns (throws/infinite loop) or unreachable type after narrowing.
  • unknown — type-safe any: anything assignable to it, but it's assignable to nothing until narrowed.

Object types

let obj: {x: number, y?: string} = {x: 1}  // y is optional
type Dict = {[key: string]: number}      // index signature
  • Arrays: number[] or Array<number>.
  • Tuples: [string, number] — fixed length & per-slot types; can label slots, support optional/rest elements.
  • enum: named set of numeric/string constants; const enum is inlined at compile time (no object emitted) — faster, less reflective.
  • type alias vs interface: aliases can name unions/primitives/tuples; interfaces describe object shapes and support declaration merging + extends.
interface Animal { name: string }
interface Animal { age: number }  // merges! Animal now needs name AND age

type ID = string | number      // union
type Both = A & B             // intersection
🪤 Trap: union (|) = "could be either," you can only use members common to all without narrowing. Intersection (&) = "must satisfy both," combines all members.
4 Functions▶

Declaring functions

function greet(name: string, greeting = 'Hi'): string {
  return `${greeting}, ${name}`
}
// rest params
function sum(...nums: number[]): number { ... }
  • Optional params (name?: string) must come after required ones; default params are optional automatically.
  • Overloads: multiple call signatures for one implementation, resolved top-to-bottom by the checker.
  • this types: you can type this as the first "fake" parameter to control method context safely.
  • Generics: function id<T>(x: T): T — preserves the specific type through a function instead of widening to a union/any.

Variance of function types (high-yield)

  • Parameters are (checked) contravariantly: a function accepting a wider/supertype param is a subtype of one accepting a narrower one — fewer assumptions about input = safer to substitute.
  • Return types are covariant: a function returning a narrower/subtype is a subtype — fine to give "more than promised."
  • Methods (vs standalone function types) are checked bivariantly by default — looser, a known unsoundness for OOP ergonomics.
function map<T, U>(arr: T[], f: (t: T) => U): U[] {
  return arr.map(f)
}
5 Classes and Interfaces▶ 
class Animal {
  private name: string
  protected readonly id: number
  constructor(name: string) { this.name = name; this.id = 1 }
  speak(): void { console.log(this.name) }
}
class Dog extends Animal {
  speak() { super.speak(); console.log('Woof') }
}
  • public (default) / private (this class only) / protected (this + subclasses) — compile-time only enforcement, erased at runtime!
  • readonly — assignable only at declaration or in constructor.
  • abstract class — cannot be instantiated directly; can declare abstract methods subclasses must implement.
  • interface describes shape only (no implementation); a class implements an interface to promise that shape; classes extend one base class but can implement multiple interfaces.
  • Because typing is structural, you don't strictly need implements at all — any matching-shape object/class is compatible.
  • Polymorphism: generic classes (class Box<T>) let one class work over many types safely.
  • Mixins — functions that take a class and return an extended class, used to compose behavior since TS lacks multiple inheritance.
🪤 Trap: private/protected are erased at compile time — at runtime, all fields are accessible like normal JS properties. They don't give real encapsulation/security.
6 Advanced Types▶

Subtyping & variance

  • Subtype: if B is a subtype of A, a B can be used anywhere an A is required. e.g. Tuple ⊂ Array ⊂ Object; never ⊂ everything; everything ⊂ any.
  • Variance kinds: covariant (preserves subtype direction — return types, readonly arrays), contravariant (reverses it — function params), invariant (must match exactly — mutable array element types in strict situations), bivariant (both directions OK — method params, looser/legacy).

Control flow / refinement

  • TS narrows types automatically based on checks: typeof x === 'string', x instanceof Foo, 'prop' in x, truthiness checks, discriminated unions, equality checks.
  • Discriminated union: each member has a common literal "tag" field so a switch/if on it narrows exactly: 
type Shape =
  | {kind: 'circle', r: number}
  | {kind: 'square', side: number}

function area(s: Shape) {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2
    case 'square': return s.side ** 2
  }
}
  • Totality — handling every case of a union (often enforced via a never-typed default branch so adding a new case breaks the build).

    • keyof / typeof / lookup types

    type Point = {x: number, y: number}
type Keys = keyof Point        // 'x' | 'y'
type XType = Point['x']      // number (lookup/indexed access)
const p = {x: 1, y: 2}
type PType = typeof p          // {x: number, y: number}

    Mapped & conditional types

    type Partial<T> = { [K in keyof T]?: T[K] }
type Readonly<T> = { readonly [K in keyof T]: T[K] }
type Record<K extends string, V> = { [P in K]: V }

type IsString<T> = T extends string ? true : false
type Unwrap<T> = T extends Promise<infer U> ? U : T

    ReturnType<T>, Parameters<T>, Pick<T,K>, Omit<T,K>, Exclude<T,U>, Extract<T,U> are all built with conditional + mapped types.

    Custom type guards & assertions

    function isString(x: unknown): x is string {
  return typeof x === 'string'
}
const el = document.getElementById('x') as HTMLInputElement  // type assertion
let y!: number   // definite assignment assertion: "I promise I'll set this before use"
    • const assertion (as const) — freezes literal types & infers narrowest possible (e.g. tuple instead of array).
    • Companion object pattern — a value (often a class or const) and a type sharing the same name, used to attach static-like behavior generically.
    • Nominal typing simulation — add a private "brand" property so structurally-identical types are no longer interchangeable.
    🪤 Trap: as / ! are unsafe escape hatches — they don't perform any runtime check or conversion, just silence the compiler. If you're wrong, you get a runtime error, not a compile error.
    7 Handling Errors▶

    Strategies (in increasing explicitness)

    • Return null/undefined — forces caller to check (especially with strictNullChecks); cheap but easy to forget to check.
    • Throw exceptions — TS can't track what a function throws in its type signature, so callers must know to wrap in try/catch by convention/docs.
    • Return an explicit "result" type (Either/Result-style union of success | failure) — makes failure visible in the type system, forces handling via narrowing.
    type Result<T> = {ok: true, value: T} | {ok: false, error: Error}

function parse(s: string): Result<number> {
  const n = Number(s)
  return isNaN(n) ? {ok: false, error: new Error('bad')} : {ok: true, value: n}
}
    • Custom error classes extend Error to carry structured info; remember to call super(message).
    • catch (e) — e is typed unknown (or any pre-4.0) since anything can be thrown; narrow with instanceof Error before reading .message.
    🪤 Trap: TypeScript has no checked exceptions — a function's type signature never tells you it might throw. That's why explicit Result/Either types are favored in TS-heavy codebases.
    8 Async, Concurrency & Parallelism▶
    • Concurrency — multiple tasks make progress over overlapping time (JS's single-threaded event loop interleaves them). Parallelism — tasks literally run at the same time (multiple threads/cores, e.g. Web Workers).
    • JS is single-threaded with an event loop: sync code runs first, then microtasks (promises), then macrotasks (timers/IO).
    function fetchUser(id: number): Promise<User> {
  return fetch(`/users/${id}`).then(r => r.json())
}
async function main() {
  try {
    const user = await fetchUser(1)
  } catch (e) { // handle rejection }
}
    • Promise<T> — generic over the resolved value; async functions always return a Promise, and await unwraps one level.
    • Promise.all — run concurrently, fails fast on first rejection. Promise.race — settles as soon as one settles. Promise.allSettled — waits for all, never rejects.
    • Generators (function* / yield) — pausable functions; typed as Generator<YieldType, ReturnType, NextType>; async generators (for await...of) combine async + iteration.
    🪤 Trap: an async function that returns T in its body is typed Promise<T> from the outside — never write async function f(): T.
    9 Frontend & Backend Frameworks▶
    • React + TS: type props with an interface; useState<T>() for generics on hooks; function components typed as React.FC<Props> (or just a typed function returning JSX).
    • Generic components: components can take type params just like functions, e.g. a generic List<T> rendering T[].
    • Node/Express + TS: type request/response generics (Request<Params, ResBody, ReqBody, Query>); use @types/express since Express itself ships untyped JS.
    • General theme: frameworks built with structural typing in mind compose well with TS generics; untyped libraries need @types packages (Ch. 11).
    type Props = {name: string, onClick: () => void}
const Button: React.FC<Props> = ({name, onClick}) =>
  <button onClick={onClick}>{name}</button>
    10 Namespaces & Modules▶
    • Module = a file with top-level import/export; has its own scope (nothing leaks globally).
    • Namespace (older namespace Foo {}, formerly "internal modules") — groups code under a global-ish named object; mostly legacy/used for ambient global typings, not for app code structure.
    • Module systems: CommonJS (require/module.exports, Node default historically), ES Modules (import/export, the modern standard), AMD/UMD (older browser/async loaders) — tsconfig's module flag picks the emitted format.
    • Declaration merging: interfaces with the same name merge; namespaces can merge with classes/functions/enums to attach extra static members.
    • Ambient modules (declare module 'foo' {...}) — describe the shape of a module that has no types of its own (e.g. importing CSS/JSON, or an untyped npm package).
    export function add(a: number, b: number) { return a + b }
import { add } from './math'

declare module '*.svg' { const src: string; export default src }
    11 Interoperating with JavaScript▶
    • allowJs — lets tsc compile plain .js files alongside .ts; checkJs additionally typechecks them (often paired with JSDoc annotations for inline types in JS).
    • .d.ts (declaration) files — contain only type info, no implementation; used to describe the shape of existing JS code/libraries.
    • DefinitelyTyped / @types/* — community-maintained .d.ts packages for popular untyped JS libraries (npm i -D @types/lodash).
    • declare keyword — tells TS "this exists at runtime, trust me, just take my word for its type" (used for globals, ambient values, and inside .d.ts files).
    • Writing your own type definitions for an untyped library is a normal real-world task — model the public API's shape as closely as possible.
    // my-lib.d.ts
declare function myLib(x: number): string

// JSDoc typing inside a .js file (checkJs)
/** @param {number} x @returns {string} */
function f(x) { return String(x) }
    12 Building & Running TypeScript▶

    Key tsconfig.json flags

    {
  "compilerOptions": {
    "target": "es2019",        // JS version to downlevel to
    "module": "commonjs",     // emitted module format
    "lib": ["dom", "es2019"], // ambient APIs available
    "strict": true,           // bundles all strict-mode flags
    "noImplicitAny": true,
    "strictNullChecks": true,
    "esModuleInterop": true,  // smoother default-import interop w/ CJS
    "outDir": "./dist",
    "sourceMap": true,
    "noEmit": false
  }
}
    • tsc typechecks AND can emit JS; many projects use Babel (or esbuild/swc) just to transpile fast, while tsc --noEmit runs only the typechecker in parallel/CI.
    • Source maps — map compiled JS back to original TS for debugging.
    • Bundlers (webpack, Parcel, esbuild) — combine modules into deployable bundles; TS integrates via loaders/plugins.
    • Monorepos / project references (tsconfig references) — let TS incrementally build multiple inter-dependent packages (faster, isolated builds) — paired with tools like Lerna/Yarn workspaces.
    • Strictness flags you should recognize: noImplicitAny, strictNullChecks, strictFunctionTypes, strictPropertyInitialization, noUnusedLocals, noImplicitReturns.
    13 Conclusion (Recap)▶

    Big picture to hold onto: types are a tool for documentation + safety, inferred wherever possible, checked structurally, and fully erased at runtime. Use the type system to make illegal states unrepresentable (discriminated unions, branded types, exhaustiveness checks) instead of relying on runtime checks/comments alone.
