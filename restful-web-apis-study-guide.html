🎯 Core Thesis: REST is an architectural style for distributed hypermedia systems. A truly RESTful API behaves like the Web itself — navigable via hyperlinks, self-describing, stateless.
Key Definitions
Resource
Any thing identified by a URL. The concept behind the URL — a product, user, document, or any named entity. Clients never see the resource directly.
Representation
A machine-readable snapshot of a resource's current state (JSON, XML, HTML). A resource can have multiple representations in different formats.
Addressability
Every resource has its own unique URL. If something is important to your application, it should have a unique name so it can be referred to unambiguously.
Statelessness
HTTP sessions last for one request. The server forgets the client after each response. All state needed to process a request must be included in the request itself.
Application State
Where the client is in its journey through the API (like page navigation). Kept by the CLIENT, not the server.
Resource State
The current data/condition of a resource on the server (e.g. a user's profile data). Kept by the SERVER.
Semantic Gap
The gap between what HTTP/media types tell you (protocol semantics) and what an API actually means for its domain (application semantics). APIs must bridge this.
Connectedness
Resources link to related resources. A client should be able to discover everything by following links, not by out-of-band knowledge.
The 6 Fielding Constraints (REST Architecture)
1
Client-Server — Separate UI concerns from data storage. Client and server evolve independently.
2
Stateless — Each request contains all needed info. No session state on server between requests. Improves scalability.
3
Cacheable — Responses must label themselves as cacheable or not. Clients/intermediaries can cache responses to improve performance.
4
Uniform Interface — The central REST constraint. Identification of resources, manipulation through representations, self-descriptive messages, HATEOAS.
5
Layered System — Client can't tell if it's connected to the end server or an intermediary (proxy, CDN, load balancer).
6
Code on Demand (optional) — Servers can send executable code to clients (e.g., JavaScript). Extends client functionality.
Uniform Interface (4 Sub-Constraints)
Sub-ConstraintMeaning
Identification of resourcesUse URIs to name resources. Each resource has a stable, unique URL.
Manipulation through representationsClients interact with resources by exchanging representations (not resources directly).
Self-descriptive messagesEvery message carries enough info to describe how to process it (Content-Type header, etc.).
HATEOASHypermedia As The Engine Of Application State — links in responses drive state transitions. No hardcoded URLs in clients.
Protocol vs. Application Semantics
Protocol Semantics
What HTTP methods and status codes mean universally. GET is always safe/idempotent. POST always creates. These don't change.
Application Semantics
What a specific API's resources and operations mean. "What does rel="flip" do?" You need a profile/documentation to know this.
Key principle: Safe = no side effects. Idempotent = calling it multiple times = same result as calling it once. Safe methods are always idempotent.
MethodSafe?Idempotent?UseBody?
GET ✅ Yes✅ Yes Retrieve a representation. Never modify state.No
HEAD ✅ Yes✅ Yes Same as GET but no body. Check metadata, existence.No
OPTIONS ✅ Yes✅ Yes What methods does this URL support? Returns Allow header.No
DELETE ❌ No✅ Yes Delete a resource. Deleting twice = same as once (already gone).No
PUT ❌ No✅ Yes Replace entire resource state. Client sends complete representation.Yes
PATCH ❌ No❌ No* Partial update. Client sends only changes. *Not idempotent by spec.Yes
POST ❌ No❌ No Create resource (POST-to-Append) or overloaded POST for anything.Yes
POST Variants
POST-to-Append
POST to a collection URL to create a new resource. Server decides the new URL. Response: 201 Created + Location header.
Overloaded POST
Using POST for any action that doesn't fit GET/PUT/DELETE. Common in older APIs. Books calls this a design smell but acknowledges it's sometimes necessary.
LINK / UNLINK (HTTP Extensions)

Non-standard methods that establish or remove relationships between resources without modifying the resources themselves. Used to link two existing resources together.

LINK /users/alice HTTP/1.1
Link: </groups/admins>; rel="collection"
Content Negotiation

Client tells server what formats it can accept. Server responds in the best matching format.

GET /user/42 HTTP/1.1
Accept: application/json, application/xml;q=0.9

Use Vary: Accept in responses so caches know different representations exist for the same URL.

Conditional Requests
HeaderUse
ETagResponse: a version tag (hash) for the current representation.
If-None-MatchGET: only send if resource changed. Returns 304 if unchanged.
If-MatchPUT/PATCH/DELETE: only apply if ETag matches (optimistic locking).
Last-ModifiedResponse: when the resource last changed.
If-Modified-SinceGET: only send if newer than date.
If-Unmodified-SincePUT: only apply if not changed since date.
Lost Update Problem: Two clients GET the same resource, both modify it, both PUT back. Second PUT overwrites first. Fix: use If-Match with the ETag. If ETag changed, server returns 412 Precondition Failed.
HATEOAS: Hypermedia As The Engine Of Application State. The server drives state transitions by embedding links in responses. Clients follow links — they don't construct URLs or have hardcoded endpoints.
What Hypermedia Is For
Guiding Requests
Out of infinite possible HTTP requests, hypermedia controls list only the ones that are useful right now in the current state.
Promises About Response
A link's rel attribute promises what kind of resource is at the other end (e.g., rel="edit" → resource you can modify).
Workflow Control
Links appear/disappear based on current state. A "Cancel Order" link only appears when the order is pending, not when shipped.
Decoupling
Clients don't need to know URLs in advance. Server can change URL structure without breaking clients that follow links.
Types of Hypermedia Controls in HTML

Link Relations

A link relation (rel) explains the relationship between the current resource and the linked resource.

Registered (IANA)
Short keywords like self, edit, next, prev, first, last, collection, item. Anyone can use these — no ownership.
Extension (URI-based)
A URL that documents the relation type: http://alps.io/example/maze/#east. Used for custom domain semantics.

Key IANA relations to know: self, edit, edit-media, collection, item, next, prev, first, last, profile, replies

URI Templates

A URL with placeholders that the client fills in. Defined by RFC 6570.

http://api.example.com/users{?name,age}

Client substitutes variables to construct the actual URL. These are "outbound links" that require client participation.

⚠️ Fake Hypermedia
Warning: A JSON field that contains a URL is NOT hypermedia. application/json has no hypermedia controls. A string that looks like a URL is still just a string.

To have real hypermedia in JSON, you must use a media type that defines hypermedia: application/vnd.collection+json, application/hal+json, application/vnd.siren+json, or JSON-LD.

Profiles

A profile adds application semantics on top of a media type without changing the media type itself. RFC 6906.

Three ways to link a document to its profile:

  • The profile link relation in <link> tag or Link header
  • The profile media type parameter: application/collection+json;profile="..."
  • JSON-LD's @context property

Collection+JSON Deep Dive

A hypermedia type designed for collections of items. Key elements:

{
  "collection": {
    "version": "1.0",
    "href": "http://api.example.com/users/",
    "links": [...],      // links to other resources
    "items": [           // list of collection members
      {
        "href": "http://api.example.com/users/42",
        "data": [        // key-value pairs
          {"name": "name", "value": "Alice", "prompt": "Full Name"}
        ],
        "links": [...]   // item-level links
      }
    ],
    "queries": [...],    // search forms (safe GET)
    "template": {        // form for creating new items
      "data": [
        {"name": "name", "value": "", "prompt": "Full Name"}
      ]
    },
    "error": {...}       // error info (optional)
  }
}
HAL (Hypertext Application Language)
{
  "_links": {
    "self":   { "href": "/orders/523" },
    "next":   { "href": "/orders/524" },
    "ea:basket": { "href": "/baskets/98712" }
  },
  "_embedded": {
    "ea:items": [ { ... } ]
  },
  "total": 30,
  "currency": "USD"
}

HAL only supports GET links. For unsafe transitions (POST/PUT/DELETE), use Siren instead.

HTML as an API Format — Microformats & Microdata
Microformats
Add semantics to HTML via class names. class="vcard", class="fn". Defined at microformats.org. Example: hCard (person), hCalendar (event).
Microdata
HTML5 attributes: itemscope, itemtype, itemprop. Links to schema.org vocabulary. More structured than microformats.
ALPS (Application-Level Profile Semantics)

A profile format that is media-type agnostic. Define your API's application semantics once, reuse across any format (Collection+JSON, HAL, Siren, HTML).

Defines two things: Semantic descriptors (what data fields mean) and Link relations (what transitions mean).

7-Step Design Procedure
Step 1: List Semantic Descriptors
What data does your API expose? List all fields and properties from business requirements. These are your semantic descriptors (e.g., title, date_posted, author).
Step 2: Draw a State Diagram
Boxes = resource states (representations). Arrows = state transitions (links/actions). Label arrows with link relations. This becomes your API's navigation map.
Step 3: Reconcile Names
Look up IANA link relations and schema.org/microformats vocabulary. Reuse existing names whenever possible. Don't invent names that already exist (e.g., use edit not update).
Step 4: Choose a Media Type
Look for domain-specific format first. If none, use Collection+JSON (CRUD collections), Siren (complex workflows), HAL (read-heavy APIs), or HTML (human + machine). Register custom media types if needed.
Step 5: Write a Profile
Document your semantic descriptors and link relations. Use ALPS for media-type-agnostic profiles. Publish the profile at a stable URL. This bridges the semantic gap.
Step 6: Implement
Write server code. Each representation should include only the hypermedia controls relevant to the current state. Don't put all controls in a single service document.
Step 7: Publish
Define a "billboard URL" (a single well-known entry point). Clients start here and discover everything else via hypermedia. Register your media type with IANA if it's general enough.

Versioning APIs
Media Type Versioning
application/vnd.myapi.v2+json. Clean, but can proliferate media types. Book's preferred approach.
Profile Versioning
Version the profile URL: http://api.example.com/profiles/v2/user. Change profile, not media type.
URL Versioning
/v2/users/. Simple but violates REST (URL should name resource, not API version).
Header Versioning
API-Version: 2 custom header. Works but not standard. Same issues as URL versioning.
Adding Hypermedia to Existing APIs
  • Can't rename existing fields (breaks clients) — add new names alongside old
  • Add links to existing JSON representations (use Link header if can't change body)
  • Use JSON-LD @context to add semantics without changing structure
  • For unsafe transitions: JSON-LD + Hydra operations
  • For XML APIs: XLink for links, XForms for forms
Anti-Patterns to Avoid
  • Service description document: One giant document describing all API URLs up front (WSDL-style). Encourages tight coupling. Breaks when API changes.
  • Autogenerating semantic names from database fields: Creates software dependency. Renaming DB fields breaks API clients.
  • Duplicating IANA link relations: Don't make up next-item when next already exists.
  • Plain JSON with URLs in fields: Fake hypermedia. URLs in JSON are just strings without a format that defines them as links.
Authentication Methods

HTTP Basic Auth Avoid without HTTPS

Username + password encoded with Base64, sent in Authorization header. Base64 is reversible — not encryption! Anyone intercepting the request can decode it immediately.

Authorization: Basic YWxpY2U6cGFzc3dvcmQ=
// Decodes to: alice:password

Problems: Not secure over HTTP (must use HTTPS). Sharing one password across many clients — if one goes rogue, you must change the password everywhere.

HTTP Digest Better than Basic

Server sends a nonce, client hashes credentials + nonce. Password never sent in plaintext. Safer than Basic without HTTPS, but has same "one password for all clients" problem.

OAuth 1.0 Per-client credentials

Solves the "shared password" problem. Each client gets its own credentials (token). Revoking one client doesn't affect others.

OAuth 1.0 Flow
1. Server gets temporary credentials
API consumer (website) requests temporary credentials from API provider — no user involved yet.
2. User redirected to API provider
User leaves your site, lands on API provider's login page. User enters password on provider's site — not yours.
3. User authorizes
User reviews permissions and approves (or denies) access for your client.
4. User redirected back
User returns to your site with an authorization code.
5. Exchange for token credentials
Your server exchanges temp credentials for permanent token credentials. Used to sign future API requests with HMAC-SHA1.
Key OAuth benefits: Per-client revocation · Provider can revoke rogue clients globally · oauth_timestamp + oauth_nonce prevent replay attacks · Works over HTTP without exposing credentials

OAuth 2.0 Modern standard

Extends OAuth 1.0 to handle desktop, mobile, and in-browser apps. Multiple "grant types" for different client types. More flexible but more complex. Requires HTTPS (no built-in signing like 1.0).
